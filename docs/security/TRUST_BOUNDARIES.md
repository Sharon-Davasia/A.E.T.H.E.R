# AETHER OS — Trust Boundaries (Phase 1 foundation)

**Status:** Phase 1 boundaries plus the merged Phase 2A resource/policy contract foundation, merged Phase 2B-1 persistence, and Stages 2–3 non-authorizing review-evidence presentation and transport; still no filesystem execution, trusted approval grants or mutations.

## Phase 1 process and module layout

| Process/module | Trust and allowed responsibility |
|---|---|
| FastAPI backend | Normal user, developer launcher binds `127.0.0.1`; peer-loopback check, ephemeral bearer session, exact-origin allowlist; typed chat/status only |
| `model_gateway` | Internal HTTP client constrained to numeric loopback, requires model-server key for inference/tokenization; no filesystem writers, shell, credentials or Windows automation imports |
| llama.cpp server | Separate ordinary-user process, `127.0.0.1`, authenticated protected routes; no tools/agent/MCP; no independent OS-action privileges |
| `model_runtime` supervisor | Verifies manifest and files, launches an exact configured executable with fixed arguments and `shell=False`, starts one server, no automatic restart; Windows Job Object containment is generated but needs target Windows validation |
| Mock tool registry | In-memory deterministic synthetic handlers only; proposals are validated but never dispatched from chat |
| `PolicyBroker` | Continues to deny every real OS action, independent of model output |

The llama.cpp server exposes an upstream minimal `/health` endpoint without API-key authentication. It is loopback-only and contains no paths or secrets. Chat and tokenization routes require a random in-memory API key passed via child environment, never command-line arguments. Loopback is not treated as authentication: backend routes separately require a bearer token. The local API token is generated at developer-server startup and displayed once in the interactive terminal, not logged or stored in the repository.

## Trust hierarchy and untrusted content

- The user is the sole authorizing principal for future consequential actions; Phase 1 does not implement approvals or actions.
- Trusted system guidance is assembled separately from user content. Only server-created user/assistant history is accepted. External evidence, if provided internally for tests, is explicitly labelled `UNTRUSTED_SOURCE`.
- Labels, system prompts, constrained JSON and Pydantic validation are not security boundaries by themselves. Security derives from module separation, authenticated loopback transport, deterministic registry validation and the deny-all real-OS broker.
- No real world-state, memory, browser, file or Windows context is available. The implementation says so rather than inventing observations.
- A local logged-in user with Windows-level access can inspect or modify same-user processes/files; AETHER does not claim to defeat a compromised local account.

## Phase 1 network and process policy

- The FastAPI developer launcher binds to `127.0.0.1`; middleware rejects non-loopback peers. Non-allowlisted `Origin` values are rejected as a request boundary. No CORS middleware or CORS response headers are present; browser-based cross-origin clients are not supported.
- The gateway accepts only numeric loopback HTTP URLs and disables ambient proxy configuration. No cloud model/provider classes or fallback exist.
- The model server binds only to `127.0.0.1` on a configurable port distinct from backend port 9931. Its protected routes use an ephemeral API key. The model server health route is public but minimal and loopback-restricted.
- Supervisor passes no user/model-generated CLI flags, does not invoke a shell, removes inherited proxy/model-hub credentials and `LLAMA_ARG_*` overrides, and sets model-hub offline mode. Built-in tools, agent and MCP proxy options are explicitly disabled.
- A model can suggest `request_tool` or `offer_rsi`; these are typed proposals only. Unknown tool IDs, invalid mock arguments and malformed structures are rejected. No output runs a command or changes policy.
- The offline unit tests constrain code paths and mock transports; they do not prove Windows firewall-level egress policy.

## Phase 2A security foundation (not executable)

The current feature branch adds `ResourceRegistry`, typed capability contracts, a configured deterministic policy path and exact approval grant contracts; details, limitations and target-Windows validation guidance are in `docs/engineering/PHASE2A_RESOURCE_POLICY.md`. This code is not yet reviewed or merged. The no-argument broker still denies all, built-in filesystem capabilities have no executor, T2 is denied because no trusted approval issuer exists, and T3 is always denied. A client-supplied approval ID or the contract's `trusted-electron` label is never authorization. No filesystem API/action or mutation surface is exposed by Phase 2A.

The resource resolver rejects unsupported path syntax (including Win32 reserved device names), registered-root escape, protected names, reparse points and volume/device identity changes. On Windows-semantics paths, a case-folded ID collision between distinct physical entries denies before replacing the existing registry mapping. Its stat-derived version token is only a freshness indicator, not a content hash or a protection against post-check races. Exact approval scope uses immutable tuple collections; `ExactApprovalGrant` is the intended authoritative Phase 2B persisted contract, while the legacy Phase 0 `ApprovalGrant` is not authorization. These broker-side checks are not an OS sandbox. No target Windows execution has been performed here, so Windows path/reparse/volume safety remains unverified. PR 2B must operationalize trusted persistent Electron approvals; PR 2C may add only verified read-only adapters; PR 2D may add only exact approved mutations and recovery after 2B/Windows security tests pass. RSI disclosure, script-worker isolation and unrelated higher-phase capabilities remain outside this milestone.

## Phase 2B-2 Stage 2 — review evidence only, never authority

Stage 2 adds an exact-preview evidence path and a trusted-review presentation. It does not add authorization.

- The backend canonical preview (`ExactPreview`) is immutable, bound to the current persisted plan revision/hash and to a lowercase SHA-256 digest of its canonical JSON. Full diff bodies never enter the digest payload, audit events, or approval records — only their SHA-256 digest does. Diff text remains user-visible evidence on the review surface, not an audit payload.
- Every Stage 2 outcome is a `NON_AUTHORIZING_AUDIT_RECORD`: Approve records audit evidence only and leaves the task `AWAITING_APPROVAL`; it grants nothing and can be replayed idempotently. REVISE returns the task to `PLANNING` and requires a fresh plan revision plus fresh consent before any later preview can be presented. REJECT terminates as `DENIED`; CANCELLED terminates as `CANCELLED`. Stale, mismatched, forged or unavailable requests never create an approval and are audited as non-authorizing STALE/UNAVAILABLE outcomes.
- Revocation (`APPROVAL_PREVIEW_REVOKED`) is an idempotent, non-authorizing invalidation event that forces fresh plan and consent for the same preview; `present()` and the persistence layer fail closed while a fresh-consent blocker exists after the latest saved plan.
- Desktop trust posture is unchanged: sandbox, context isolation, CSP, `file://`-only navigation, per-launch HMAC session, authenticated child transport, fixed narrow IPC with sender/frame/focus validation. Stage 2 adds exactly two channels (`desktop:review-preview`, `desktop:record-review-outcome`) whose arguments are re-parsed in main before reaching an interface-bound provider. The shipped provider is fail-closed: the review surface reports unavailable and no control can record anything. No `ExactApprovalGrant` issuance, storage or consumption, no T2/T3 path, no filesystem adapter, no user-file mutation, and no generic privileged renderer IPC are introduced.
- The Stage 1 authenticated child protocol still carries only a synthetic ping; no backend review transport is wired to the desktop provider. Displaying or recording a real preview requires a future, separately reviewed protocol change.
- Stage 2 is Linux-verified only for the code paths exercised; no Windows execution or security acceptance is claimed for it. Review-surface wording keeps review evidence, authorization and execution distinct; a user clicking Approve performs no action and issues no capability.

## Phase 2B-2 Stage 3 — authenticated exact-preview delivery and non-authorizing decision transport

Stage 3 transports the Stage 2 review evidence over the Stage 1 authenticated channel. It does not add authorization. The independent review of PR #12 produced corrections S3-1 (audit-only lost-acknowledgement reconciliation via the added `review.get_outcome` operation, justified above), S3-2 (narrative-source I/O failures converted into bounded unavailable responses) and S3-3 (hardened `-P -I -B -u` launch). No correction changes the boundary: nothing here issues, stores or consumes a grant.

- The only backend operation kinds are `review.get_preview`, `review.record_outcome` and `review.get_outcome` (`python -P -I -B -u -m aether.channel.service`; the hardened launch implies `-E`/`-s` via `-I` and safe-path via `-P`, so the child imports only from the interpreter's own site-packages). No generic privileged operation exists; an unknown kind terminates the session. All request payload validation lives in the bridge's defensive entry points: malformed/extra-keyed/oversized requests produce bounded typed failures and are never raised as exceptions into the request path. Narrative-source I/O failures (deleted, unreadable, directory-replaced or oversized seed file) convert into the same bounded `review_unavailable` contract and never raise into the request path.
- `review.get_outcome` is an audit-only reconciliation operation added for lost acknowledgements. It is strictly read-only: no audit event, no state transition, no preview presentation, no narrative requirement. It verifies the exact immutable request identity (task, plan revision/hash, preview identity, request id, requested outcome) against the persisted approval record or Stage 2 audit event and returns the persisted acknowledgement (`idempotentReplay: true`); otherwise it answers `not_recorded` or `review_conflict`. It creates no new stale decision, infers no authorization, and reports persistence only on authoritative persisted evidence. Its justification: without it, an exact idempotent retry after a lost acknowledgement could not confirm a previously persisted decision (especially after a terminal transition such as DENIED/CANCELLED, where no preview is presentable), forcing either a false failure receipt for a persisted decision or a fresh, user-visible re-decision.
- `review.get_preview` returns either a typed `ready` preview bound to one reviewable persisted PREVIEW_READY/AWAITING_APPROVAL task, or a typed non-success (`review_unavailable`, `invalid_task`, `preview_too_large`). The preview is the same canonical artifact digest-bound in Stage 2; the full diff never enters the digest payload, audit events, or approval records.
- `review.record_outcome` records exactly one Stage 2 bounded outcome (APPROVE/REJECT/REVISE/CANCELLED) through `PreviewReviewService` and returns either the non-authorizing acknowledgement (`NON_AUTHORIZING_AUDIT_RECORD`, `granted: false`, `executionAvailable: false`, `auditPersisted: true`, carrying `requestedOutcome` and `idempotentReplay`) or a bounded typed failure (`invalid_review_request`, `review_unavailable`, `review_conflict`). Failure never produces an acknowledgement; nothing is persisted on the failure paths.
- Trusted main-process provider (`electron/channel-review-provider.ts`) verification order: (1) backend state must be `ready`; (2) wire payloads re-parse as the exact bounded contract; (3) `verifyExactPreviewDigest` plus `previewIdForDigest`/`reviewRequestIdForDigest` must match the backend-supplied identity fields; (4) the delivered `taskId` must equal the trusted main-process-configured task (never renderer-controlled; unset in packaged builds — fail closed); (5) recording re-fetches and re-verifies the current persisted preview and requires the submitted request to match it field-for-field, refusing drift before any byte is sent; (6) the acknowledgement must parse, carry the submitted `requestedOutcome` and non-granting semantics — otherwise no success is shown. Every failure mode is `unavailable` (presentation) or an error without receipt (recording).
- Development-only synthetic scenario (`AETHER_REVIEW_DEV_SEED=synthetic-review`, fixed synthetic task id, synthetic canary) exists so end-to-end evidence can be produced with real persistence and real digests without touching user data; it writes only development-database audit rows and is never activated by packaged builds. `AETHER_REVIEW_DB`/`AETHER_REVIEW_NARRATIVE` are absolute-path-only development seams; the renderer can neither see nor influence them. A narrative-source failure is never silently masked by falling back to another source; without configuration the review surface reports unavailable by design. No production narrative source exists yet (the future Phase 2 planner is that source).
- Desktop trust posture is unchanged: four fixed preload calls, sender/frame/file-URL/focus validation in main, no renderer access to `shared/review-integrity.ts` or the provider, per-launch HMAC session, bounded frames, no new ports or hosts. `review.error` frames reject with a bounded machine-readable reason (`invalid_review_request`, `review_unavailable`, `review_conflict`, `not_recorded`); unexpected kinds/pending mismatches are protocol violations and tear down the session. Oversized previews fail closed with `preview_too_large` rather than an undeliverable frame. In the provider, a drifted submission is never reconciled (drift refusal stands); reconciliation runs only when the preview is not presentable, the record acknowledgement was lost or unparsable, and it returns only persisted audit evidence — never a fresh decision.
- Launch posture: the child is spawned with `-P -I -B -u -m aether.channel.service`. `-I` implies `-E` (ignores `PYTHON*` environment variables including `PYTHONPATH`, `PYTHONHOME`, `PYTHONUSERBASE`) and `-s` (suppresses user site-packages); `-P` (Python >= 3.11, safe_path) removes the cwd/script directory from `sys.path`. Imports therefore resolve only through the selected interpreter's own installation metadata. `-I` does not prove that every module physically resides in `site-packages`: an editable development install legitimately imports the AETHER source checkout through an installed `.pth`/editable finder. Development expects a trusted, selected interpreter with a controlled editable or installed AETHER package; packaged releases (future) must use a non-editable, verified package installation with independent import-provenance and dependency/integrity verification as required by the Master Specification. No uncontrolled `PYTHONPATH`/user-site/cwd injection exists at run time. The child environment is a fixed minimal allowlist (plus absolute-path development review seams) with no `PYTHON*` entries. The parent-side interpreter selection remains environment-controlled in development (`AETHER_DEV_PYTHON`) and pinned in expectation (`AETHER_DEV_PYTHON_VERSION`, packaged default 3.12.10).
- Replay semantics are audit-only and idempotent: an exact replay of a persisted request returns the recorded outcome as `idempotentReplay: true` and never a new grant; a changed outcome or drifted preview fails closed (`review_conflict` / refused at verification).
- No production schema migration is included or authorized; `0001_phase2b_core.sql` fingerprint unchanged (the reconciliation lookup reuses the Stage 2 read paths and adds no storage). No `ExactApprovalGrant` issuance/storage/consumption, no T2/T3 path, no filesystem adapter, no user-file mutation, no auto-merge, no Phase 3 work. Independent review of this stage is pending; merging is a separate decision.
- Stage 3 is Linux-verified only; no Windows execution or security acceptance is claimed. Requirements-to-test mapping lives in the Stage 3 desktop README section and the PR description.
- **Digest verification ownership:** the renderer is never the verification or approval authority. The trusted main-process provider on the authenticated channel (future milestone) must recompute and verify the canonical digest, preview ID and review request ID against backend-supplied values before returning a preview to the renderer and before recording any outcome. Node-side verification helpers (`shared/review-integrity.ts`) are pinned to the backend by a generated golden fixture and are never imported by renderer code. Until a trusted provider exists, the default provider is fail-closed and no preview can be shown or recorded.
- Stage 2 outcomes distinguish review evidence from authorization: the full-diff acknowledgement is required for APPROVE only; REJECT/REVISE/CANCELLED never imply inspection or acceptance. Audit events persist the requested outcome (`requested_outcome`) so replay with a changed outcome or changed preview data fails closed, including across store close/reopen.
