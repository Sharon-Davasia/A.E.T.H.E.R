### Phase 2B-2 Stage 3 — independent-review corrections (merged with PR #12)

Independent source review accepted the architecture direction but required three corrections before merge. All three were implemented on the Stage 3 branch and are merged in PR #12.

- **S3-1 — Lost-acknowledgement reconciliation.** New narrow, read-only operation `review.get_outcome`: same bounded request schema as `review.record_outcome`; responds with the persisted acknowledgement for the exact immutable request identity (task, plan revision/hash, preview/request identity, requested outcome) proven by the approval record or Stage 2 audit event — `idempotentReplay: true` — or `not_recorded` / `review_conflict` / bounded failures. It never writes audit data, never transitions state, never presents a preview and requires no narrative source, so it confirms a previously persisted decision after a lost acknowledgement, after a terminal transition (DENIED/CANCELLED), after a REVISE (task returned to PLANNING) or after a full process restart. No new stale decision is created; no authorization is inferred; a drifted submission is never reconciled (the provider refuses it before any send). In the provider, reconciliation also covers a lost or unparsable record response; a missing record surfaces as an explicit non-receipt error instructing the user to re-record explicitly. The operation's justification: without it, an exact idempotent retry after a lost acknowledgement cannot confirm the persisted decision the backend already committed. Transport unchanged otherwise (same HMAC/session/bounds, same frame rules).
- **S3-2 — Narrative-source I/O failure.** `ReviewBridge._load_narrative` converts source-read failures (file deleted, directory-replaced, unreadable, oversized, replaced with an invalid/cross-task/malformed seed) into the existing bounded unavailable contract (`review_unavailable`) for both `review.get_preview` and `review.record_outcome`; nothing is acknowledged, no record is written, and the channel remains usable for subsequent permitted requests. No fallback to another narrative source is performed silently.
- **S3-3 — Hardened launch.** The child is spawned with fixed `-P -I -B -u -m aether.channel.service` (`-I` implies `-E`/`-s`: ignores `PYTHON*` env including `PYTHONPATH`/`PYTHONHOME`/`PYTHONUSERBASE` and suppresses user site-packages; `-P` safe_path, Python ≥ 3.11, removes cwd/script directory from `sys.path`). Imports resolve only through the selected interpreter's own installation metadata; `-I` does not prove physical module location — an editable development install legitimately imports the source checkout via an installed `.pth`/editable finder. Development: trusted selected interpreter with a controlled editable or installed AETHER package. Packaged release (future): non-editable verified package installation with import-provenance and integrity verification per the Master Specification (not implemented in this PR). No uncontrolled `PYTHONPATH`/user-site/cwd injection remains. Regression evidence: subprocess test with a hostile `PYTHONPATH` shadow package (sentinel never loads), a `sys.path` assertion (no cwd/user-site entries), a hostile-`PYTHON*` import test and an import-origin probe reporting the module resolution path; desktop integration test asserts the exact spawned argument vector and a `PYTHON*`-free child environment.
- Corrections added 19 backend tests (`backend/tests/test_phase2b_stage3_corrections.py`), 7 desktop live-channel integration tests (total 7 incl. reconciliation-after-restart and hardened-argparse) and 8 provider unit tests (lost-ack reconciliation semantics). Backend subprocess tests now themselves use the hardened flags.
- **Windows requirements (unchanged, still pending):** run the Stage 3 child-launch verification on the target laptop — fixed `-P -I -B -u -m aether.channel.service` arguments, child environment free of `PYTHON*` variables, import provenance for the `aether` package consistent with the selected installation mechanism (editable `.pth` in development; non-editable verified installation for any future packaged release), handle-inheritance behavior, Job Object/process-cleanup behavior. No Windows claim is made.
