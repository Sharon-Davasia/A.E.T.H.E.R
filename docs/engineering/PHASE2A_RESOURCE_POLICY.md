# Phase 2A — Resource and policy foundation

**Status:** Broker-side foundation on the current feature branch; PR #5 has been reviewed and the requested corrections are implemented pending re-review. It is not merged. Phase 2A does not expose filesystem execution or mutation and is not Phase 2 acceptance.

## What this milestone adds

- `ResourceRegistry` accepts explicitly registered absolute directory roots with narrow capability IDs. It rejects volume roots, unknown/non-fixed volumes by default, secrets/protected paths, reparse components, and unsupported resource types. Registry-issued `file:<uuid>` / `directory:<uuid>` references contain no raw path. Each resolution is constrained to its root and checked against volume/device identity; references carry a deterministic stat/version digest and must be re-resolved before authorization.
- Relative resource names use Windows path rules on every host OS. Drive/UNC/device paths, parent traversal, alternate data streams, reserved device names, invalid components and sibling-prefix escapes are rejected. Reserved basenames include `CONIN$`, `CONOUT$`, and `COM`/`LPT` followed by 1–9 or superscript ¹/²/³, case-insensitively and even with extensions or nested path components. Existing symlinks/junctions/reparse points are denied. Root-level and child-level volume identity must remain stable.
- On Windows-semantics registries, case-folded canonical resource-ID collisions between different physical entries fail closed with `resource_identity_collision` before the existing registry entry can be overwritten. A changed file identity at the exact same canonical relative path is treated as replacement: fresh resolution refreshes the registry mapping and version token, so previously issued refs fail version validation. A target Windows case-sensitive-directory/reparse/volume test is still required.
- Capability contracts are an explicit typed allowlist with strict argument schemas, declared resource kind, risk tier and data-class ceiling. Unknown capabilities and malformed arguments deny. T3 always denies. The no-argument broker retains Phase 0/1 deny-all behavior. `fs.inspect_file` is defined as metadata-only (type, size and modified time; no content bytes) and classified T0; any future content-reading behavior is a new T1 operation. Every Phase 2A filesystem contract remains non-executable; even a syntactically valid `approval_id` cannot enable T2.
- `ExactApprovalGrant` is the intended authoritative Phase 2B persisted contract; the legacy Phase 0 `ApprovalGrant` is not a Phase 2 authorization. Exact grant operations/resources are immutable tuples containing frozen nested models. The grant binds task, plan revision/hash, step, capability, tier, canonical arguments/effect hashes, resource IDs and versions, expiration, revocation and bounded uses. A deterministic matcher checks exact equality. Phase 2B must persist and verify the scope digest alongside the stored immutable grant and authenticate trusted Electron-main input. The contract's `trusted-electron` marker is data, not proof. Phase 2A provides no issuer, store, IPC, HTTP approval route or mutation adapter.

## Fail-closed limitations and security notes

This is broker-side validation, not a filesystem sandbox. It does not prevent a same-user attacker or a concurrent filesystem race after resolution. Windows reparse-point inspection, volume identity, file-handle identity, and TOCTOU-safe access require target Windows implementation and adversarial verification. Mutation code must open handles without following reparse points, verify volume/file identity and expected version immediately before use, and never trust a display path or a model/client-provided grant. Current version tokens use volume/device/file identity plus size, nanosecond mtime and mode; they are freshness guards, not content hashes or cryptographic file identity proofs. Missing-leaf resolution is for future controlled planning only and does not create files.

Protected-name matching is conservative but cannot infer that every arbitrary user file contains a secret. Future UX and data-classification rules must preserve deny-by-default access for secret locations/content. Unknown Windows volume/reparse behavior must remain a denial. No content is logged by these helpers.

No target Windows execution has been performed in this environment; Linux tests with synthetic directories/fixed volume inspectors are not evidence of Windows 11 safety. Test guidance for the eventual Windows run:

1. Use Python 3.12.10, PowerShell, uv, and a disposable `D:\A.E.T.H.E.R` checkout; do not place fixtures in personal project folders.
2. From the D: checkout root, run `powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\verify.ps1`. Its pytest step runs `uv run pytest --basetemp $pytestBase`, where `$pytestBase` is `<repository>\.cache\pytest-tmp` on D:. Thus the `tmp_path` synthetic registry fixtures avoid `%LOCALAPPDATA%\Temp`; do not weaken protected-path rules to accommodate pytest defaults.
3. Add/run dedicated Windows tests for drive-relative paths, drive roots, UNC/device namespaces, junctions and symlinks, mount/reparse crossings, case-insensitive identity, a case-sensitive NTFS directory containing distinct `A.txt`/`a.txt`, atomic `os.replace()` and stale-reference denial, alternate data streams, `COM¹`/`LPT²`/`CONIN$`/`CONOUT$` device names with mixed case/extensions/nesting, sibling-prefix escapes, changed volume/file IDs, hard links, and operations racing root replacement.
4. Verify that a removable/network/unknown volume, protected/secret path, stale reference, forged reference, unknown capability, unsupported operation and every T3 operation yields deny with no access and no file changes.
5. Confirm no mutation route or executor is reachable in 2A, and that changing a syntactically supplied client `approval_id` never changes policy outcome.
6. Record exact Windows OS/Python/PowerShell/uv versions and command outputs. Do not mark Windows safety accepted without successful execution and review of the actual Windows results.

## Follow-on sequence

- **PR 2B:** durable task/plan/approval storage, one-use/revocable/expiring grant lifecycle, and authenticated trusted Electron-main approval channel; tests for spoofed IPC, forged/stale/replayed grants, restart semantics and atomic consumption. Still no mutation unless trust validation is operational.
- **PR 2C:** read-only filesystem listing/open/search through verified handles, bounded outputs, secret redaction/denial and trusted-root UX; keep all writes unavailable.
- **PR 2D:** exact approved edit preview/apply, independent content/version checks, receipts/snapshots, safe recovery/Undo and verified end-to-end Windows demo. Gate every mutation on trusted 2B authorization and platform-specific handle checks.

The response-quality regression suite and examples are a separate workstream; they must not expand scope or delay these security PRs. The longer-term Phase 2 acceptance in `docs/architecture/MASTER_SPEC.md` remains authoritative; this milestone satisfies none of its end-to-end mutation/Undo gates by itself.
